# 01 · The Struct Skeleton (Python)

## Setup

This step (and every later Python step) shares a single virtualenv at the
**repo root**, so it only needs to be created once:

```bash
# from the repo root
python3 -m venv .venv
source .venv/bin/activate
pip install -r week1_baseline/python/01_struct_skeleton/requirements.txt
```

The launcher at `week1_baseline/bin/python/01_struct_skeleton` assumes
`.venv` already exists at the repo root and has these dependencies
installed.

---

Let's define data structures for specific data we need to constantly pass around.
- `boukensha.Tool`
- `boukensha.Message`
- `boukensha.Context`

Ruby represents these as `Struct`s for lightweight, readable data classes. The
Python equivalent is `@dataclass` — same idea: fields declared up front, a
custom `__str__` for the readable repr shown below, and no framework/schema
layer on top.

## Data Structures

### `boukensha.Tool`
| Field | Description |
|---|---|
| `name` | The name of the tool |
| `description` | Shown to the agent so it knows when to invoke the tool |
| `parameters` | The arguments that need to be passed in |
| `block` | The actual code that runs when the tool is called |

**Examples:**
```
#<Tool name=move description="Move the player in a direction (north, south, east, west, up, down)" params=['direction']>
#<Tool name=attack description="Attack a target in the current room" params=['target']>
#<Tool name=look description="Look around the current room" params=[]>
#<Tool name=say description="Say something out loud to others in the room" params=['message']>
```

(The Ruby version prints `params=[:direction]` — symbol syntax. Python has no
symbol type, so `parameters` is a plain string-keyed dict and prints as
`['direction']`. This is the one expected shape difference from the Ruby
output.)

### `boukensha.Message`
A single unit of conversation between the user and the agent.

| Field | Description |
|---|---|
| `role` | Who is speaking — user, assistant, or tool_result |
| `content` | The text generated by the agent or provided by the user |
| `tool_use_id` | Links a tool result back to the specific tool call that requested it. The API requires this pairing to be exact. |

**Examples:**
```
#<Message role=user content=Explore north and tell me what you find....>
#<Message role=assistant content=Sure, let me head north and take a look....>
#<Message role=tool_result [toolu_01X] content=You move north into a torch-lit corridor....>
```

### `boukensha.Context`
Holds everything BOUKENSHA needs to make an API call. Nothing lives outside of this.

| Field | Description |
|---|---|
| `system` | Tells the agent what its job is. Sent as a separate field in the API call, never inside the messages array. |
| `messages` | The full conversation history, replayed on every turn |
| `tools` | The registered tools the agent is allowed to invoke |

```
#<Context task=player turns=2 tools=1>
```

## Config directory resolution

Unchanged from `00_config` — the class looks for a `.boukensha/` directory
in this order:

1. **`BOUKENSHA_DIR` env var** — set this to point at any directory you like.
2. **`~/.boukensha`** — the default location for a real install.

```
.boukensha/
  .env                 # stores credentials eg. LLMs APIs (never committed to repo)
  settings.yaml        # all non-secret settings
  prompts/
    <task>/
      system.md        # per-task override for the default system prompt (optional)
```

Note: unlike `00_config`, this step's `Config` has **no `PROMPTS_DIR`**
constant and ships no default `prompts/system.md` — the system prompt in the
example below comes entirely from the user's own
`.boukensha/prompts/player/system.md` override (or is `None` if that file
doesn't exist).

## Considerations
These are things we observed but we do not want fixed since future steps will break.
- `Config.__str__`, `Context.__str__`, `Tool.__str__`, and `Message.__str__`
  all keep the `#<...>`-style Ruby repr for parity with the Ruby port,
  rather than Python's usual `ClassName(field=value)` dataclass repr —
  matches the 1:1 porting goal for this step.

## Naming conventions for this port

- Ruby's `prompt_override?` is `is_prompt_override` here (not a bare
  `prompt_override`, since that name is already the settings dict key —
  keeping the `is_` prefix avoids the clash). Apply this convention to any
  future `?`-suffixed method ported from Ruby.
